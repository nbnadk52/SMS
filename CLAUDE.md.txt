# CLAUDE.md - SMS

## Overview
SMS is a student and administrative management system for academic records, employee management, payroll workflows, and user administration. The target production-ready architecture is a modern .NET 10 ASP.NET Core Web API using ControllerBase endpoints, an Angular frontend, and the proven enterprise patterns already familiar to the team: repository abstraction, Autofac dependency injection, EF Core persistence, and ASP.NET Identity security.

This is the right senior-dev choice for the current phase: keep the solution stable, make it easier to onboard and maintain, and modernize incrementally without forcing a risky rewrite.

## Recommended Stack
- .NET 10 SDK
- ASP.NET Core Web API with ControllerBase
- Angular frontend for UI, dashboards, and CRUD screens
- Entity Framework Core 10 with PostgreSQL for persistence
- Repository pattern for data access abstraction
- Autofac for dependency injection and module registration
- ASP.NET Core Identity for authentication and authorization
- JWT bearer tokens for API clients where needed; cookie auth for server-side sessions when appropriate
- FluentValidation for request validation
- Scalar for API documentation
- Serilog for structured logging
- xUnit + FluentAssertions for testing
- Docker for local environment parity and deployment readiness

## Production-Ready Principles
- Prefer stability and maintainability over trend-driven rewrites.
- Keep business logic in service and domain layers, not in controllers.
- Keep controllers thin and consistent.
- Design for predictable deployment, observability, and supportability.
- Use secure defaults and explicit authorization rules.
- Do not add complexity without a business need.

## Project Structure
- `src/SMS.Api/` - controllers, routing, middleware, filters, startup, and API configuration
- `src/SMS.Application/` - application services, DTOs, contracts, validators, and use-case orchestration
- `src/SMS.Domain/` - entities, value objects, enums, domain rules, and shared contracts
- `src/SMS.Infrastructure/` - EF Core DbContext, repositories, persistence implementations, and external integrations
- `src/SMS.Client/` - Angular application, services, components, and shared UI modules
- `src/SMS.Shared/` - shared DTOs, constants, enums, and common contracts used by API and client
- `tests/SMS.UnitTests/` - service, repository, and domain logic tests
- `tests/SMS.IntegrationTests/` - API endpoint and real flow validation tests
- `docs/` - architecture notes, runbooks, and onboarding guides
- `scripts/` - database, build, deployment, and automation scripts
- `deploy/` - CI/CD and environment configuration

## Commands
- Restore: `dotnet restore`
- Build: `dotnet build`
- Test: `dotnet test`
- Run API: `dotnet run --project src/Api`
- Run Angular app: `npm install && npm start --prefix src/SMS.Client`
- Add migration: `dotnet ef migrations add <Name> -p src/SMS.Infrastructure -s src/SMS.Api`
- Update database: `dotnet ef database update -p src/Infrastructure -s src/Api`
- Format: `dotnet format`
- Run API with logs: `dotnet run --project src/Api --urls "https://localhost:5001;http://localhost:5000"`

## Architecture Rules
- Use the repository pattern through `IRepository<T>` and concrete repository implementations.
- Repository interfaces must be explicit and readable; no ad hoc query logic in controllers.
- Use Autofac for dependency injection and module registration.
- Register services and repositories through Autofac modules such as `ServiceModule`, `RepositoryModule`, and `EFModule`.
- Keep API controllers focused on request validation, authorization checks, model binding, and response shaping.
- Keep business logic in services and domain models rather than in controllers.
- Treat the API as the system boundary and do not allow UI or client code to bypass validation or authorization.
- Use controllers and route-based APIs rather than minimal APIs for this project unless a business need justifies a migration.
- Keep security concerns at the edge of the system and centralize them in the infrastructure and auth pipeline.
- Prefer explicit, maintainable refactors over speculative architectural rewrites.

## Patterns We Use
- ControllerBase-based API controllers with `[ApiController]`
- Repository pattern with generic `IRepository<T>` and `Repository<TEntity>`
- Autofac `ContainerBuilder` and module-based composition root
- Constructor injection across controllers, services, repositories, and validators
- EF Core `DbContext` and `DbSet<TEntity>` for persistence
- ASP.NET Core Identity for authentication and user management
-  Always pass CancellationToken to async methods
- Authorization through `[Authorize]`, `[AllowAnonymous]`, roles, and claims
- Validation in FluentValidation and model validation before business work begins
- DTO-based request and response contracts
- Service-oriented business workflows for lookups and domain operations
- Structured logging and error handling at the middleware and service boundaries

### Patterns We DON'T Use (Never Suggest)
- Direct `DbContext` access from controllers or UI code
- Bypassing repository abstraction for basic CRUD work
- Service locator or manual resolution from static containers
- Minimal API rewrite without a business-driven migration plan
- AutoMapper by default when explicit mapping is clearer and easier to audit
- Hardcoded authorization bypasses that ignore ASP.NET Identity and security middleware
- Stored procedures for routine CRUD unless there is a very specific operational requirement
- Over-engineering with speculative frameworks or layered abstractions that are not used by the team

## Authentication and Authorization
- Use ASP.NET Core Identity for user creation, login, password flow, and security stamp validation.
- Use secure cookie authentication for server-driven sessions and JWT bearer authentication for API clients when required.
- Keep all protected API endpoints behind `[Authorize]` and secure all admin or sensitive modules explicitly.
- Public endpoints must use `[AllowAnonymous]` and must be clearly justified.
- Centralize permission checks around Identity roles, claims, and policy-based authorization.
- Do not bypass the framework pipeline with custom auth logic.
- Validate session and token expiration, refresh flows, and failure handling consistently.
- For Angular clients, use secure session handling and explicit API authorization checks on each protected route.

## Dependency Injection and Autofac
- Register controllers with the ASP.NET Core dependency system and Autofac integration.
- Register repositories using `RepositoryModule` and generic scanning patterns.
- Register application services through `ServiceModule`.
- Register infrastructure dependencies through `EFModule` or equivalent composition-root modules.
- Use `InstancePerLifetimeScope()` or the appropriate lifetime for repositories and services.
- Do not construct dependencies manually inside controllers, services, or business logic.
- Keep composition root configuration in startup and modules, not scattered through the solution.

## Validation and Request Handling
- Validate `ModelState` before business processing in controller actions.
- Use FluentValidation for request validation and enforce consistency across endpoints.
- Prefer clear validation and controlled error responses over exception-driven control flow.
- Avoid accepting invalid state, incomplete payloads, or unauthorized actions silently.
- Return consistent API error contracts for 400, 401, 403, and 404 responses.
- Use centralized exception middleware for infrastructure-level issues and safe, sanitized responses.

## Error Handling and Observability
- Use middleware for unhandled exceptions and correlation IDs.
- Log request/response metadata, status codes, correlation IDs, and user context when safe.
- Do not expose internal stack traces or sensitive errors to client applications.
- Standardize API error payloads so clients can handle business and system failures predictably.
- Ensure health checks are available for database, dependencies, and critical services.

## Testing
- Unit tests cover domain rules, repositories, and service logic.
- Integration tests validate real API flows, auth behavior, and persistence boundaries.
- Test names follow `[Method]_[Scenario]_[ExpectedResult]`.
- Validate secure routes and permission checks in integration tests.
- Avoid brittle tests that assert implementation details instead of behavior.
- Prefer real behavior and integration contracts over mock-heavy tests.

## Angular Guidelines
- Use Angular services for all API integration.
- Prefer typed models and clean DTO contracts over `any`.
- Keep components focused on presentation, user interaction, and state management.
- Use environment configuration for API base URLs and environment-specific settings.
- Handle protected routes and auth state explicitly in the client.
- Keep API contracts consistent and versioned across modules.

## Security and Production Standards
- Use HTTPS in all non-local environments.
- Store secrets in secure configuration providers, not in source control.
- Enforce authorization on all protected endpoints and administrative modules.
- Validate all input at the API boundary and sanitize output where needed.
- Restrict database and infrastructure access to least privilege.
- Add rate limiting, CSRF protection where needed, and secure cookie settings for browser-based flows.

## Deployment and Operations
- Use environment-specific configuration for development, staging, and production.
- Add health checks and readiness endpoints for infrastructure monitoring.
- Use CI pipelines for build, test, and packaging validation.
- Standardize deployment scripts and rollback procedures.
- Ensure logs, database migrations, and release steps are documented and repeatable.

## Git Workflow
- Branch naming: `feature/`, `bugfix/`, `hotfix/`
- Commit format: `type: description` (feat, fix, refactor, test, docs)
- Always create a branch before changes
- Run relevant tests before committing
- Keep pull requests focused on one business concern at a time
- Require code review for security-sensitive or business-critical changes

## Code Quality and Senior Guidance
- Favor simple, explicit code over clever abstractions.
- Keep the dependency graph understandable for the current team.
- Prefer readable and maintainable code over trendy architecture churn.
- Do not introduce new patterns unless there is a real production need.
- If modernization is required, do it in stages with migration compatibility and rollback planning.
- Use conservative, battle-tested patterns when the application is already in active use.
